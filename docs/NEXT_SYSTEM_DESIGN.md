# 《沧衡纪》vNext 最终系统设计方案

> 文档状态：设计冻结候选稿
> 基于版本：V1.0 / schema 3 / commit `b350438`
> 日期：2026-08-25
> 本轮范围：只做架构与产品方案，不实现 P0/P1 功能

## 1. 最终判断

当前项目已经证明了“世界会运转”：82 个陆地区域、10 个海域、人口与粮食守恒、贸易与迁徙、疾病、知识、人物、家族、派系、外交、战争、史册和存档都能长期确定性运行。

下一阶段不应继续横向增加资源、兵种、文化或地图。真正的产品缺口是：

> 世界会发生很多事，但玩家还不能稳定地跟完“一件事如何持续数年并改变一代人”。

vNext 的唯一主目标因此定义为：

> 把现有的丰富模拟，组织成玩家可以发现、关注、等待、理解、回看的一段段持续历史。

最终衡量标准不是系统数量，而是：一个世界运行 50 年后，玩家能否自然讲出 5～10 段带人物、动机、转折和结果的历史。

## 2. 本阶段的产品北极星

### 2.1 玩家循环

```text
打开世界
  ↓
看到 2～4 条正在发展的历史局势
  ↓
选择一条关注并作出自己的判断
  ↓
推进季度 / 自动推演
  ↓
局势因人物行动、资源和制度发生可解释变化
  ↓
关键转折自动暂停
  ↓
查看“上一季发生什么、为什么、接下来观察什么”
  ↓
局势解决，生成一段可回看的历史总结
  ↓
结果进入人物记忆、家族史和下一轮目标
```

### 2.2 首个纵向切片

第一个完整切片选择“北境军权危机”，而不是同时实现所有 Situation：

```text
年轻副将参与真实战斗
→ 累积战功与统军经历
→ 形成“获得独立统军权”目标
→ 培养军中关系并争取家族支持
→ 升任主帅或获得新军
→ 朝廷因其势力增长而警惕
→ 削权、召还、调任或安抚
→ 将领形成新的记忆与计划
→ “军权危机”进入当世三问
→ 归顺 / 妥协 / 被清洗 / 拒令 / 起兵
→ 形成局势结案、人物传记与家族后果
```

这个切片同时验证 Fact、人物 AI、家族、Situation、战争、史册和观察 UX，是最小但完整的 vNext 证明。

## 3. 真实现状评估

### 3.1 已经做对的部分

| 能力 | 当前价值 | vNext 决策 |
|---|---|---|
| 确定性随机 | `seed + turn + system + entity + purpose` 独立寻址 | 完整保留；任何新 AI 都不得使用 `Math.random` |
| 世界守恒 | 人口、粮食、财富、商品、运输、疾病分舱均有账本与 invariant | 保留为模拟底座，不在叙事改造中重写 |
| 因果事件 | `HistoryEvent` 已有原因、证据和状态差量 | 拆分 Fact 与 Chronicle 后继续作为兼容投影 |
| 关系记忆 | 有向关系、信任/恐惧/积怨/感激、每边最多 8 条记忆 | 继续使用；补个人记忆，不复制一套政治记忆数组 |
| 背景人物池 | `BackgroundPersonState` 可按需升级并保留来源 | 作为真正 Simulation LOD 的基础 |
| 观察工具 | 当世三问、关注、自动暂停、历史工作台、领土回拨 | 改为 Situation 的主要入口，不推倒 UI |
| 长程验证 | 87 项测试、确定性、守恒、存读档、浏览器 E2E 和多种子审计 | 新增叙事质量审计，不替代现有正确性测试 |

### 3.2 结构性问题与代码证据

| 问题 | 当前证据 | 影响 |
|---|---|---|
| 没有持续故事实体 | `src/view/observer-leads.ts` 每次从裸 WorldState 重新评分，WorldState 没有 Situation | 三问容易换题，玩家看不到同一矛盾的连续发展 |
| Fact 与史册耦合 | `resolveBattle` 每场都结算，但 `engine.ts` 仅冬季第一场写 `battle` 事件 | 真实发生不等于被系统感知 |
| 副将成长漏算 | `processV02MilitaryCareers` 只消费当季 `HistoryEvent.kind === battle` | 非冬季战斗、同季后续战斗和战后解散军团可能不给经历 |
| 人物没有持续意图 | `CharacterState` 没有 Desire/Goal/Plan；政变、抗命和叛乱仍是公式过阈值 | 行为有解释，但缺少“他几年前就在准备”的历史连续性 |
| UI“所求”不是模拟事实 | `src/view/adapters.ts` 仅按野心、忠诚临时生成两句文案 | 玩家看到的是推断标签，不是人物真实目标 |
| LOD 只是标签 | `tier` 不改变计算；开局 192 名具名人物几乎都会进入“核心” | 未来扩展人物后无法控制 AI 和记忆成本 |
| 家族过碎 | 实测种子开局 172 家族，其中 164 个单人家族，最大家族 5 人 | 家族更像人物附属记录，难形成跨代政治主体 |
| 家族财富语义不清 | `updateFamilyMetrics` 每年直接增加 `family.wealth`，未进入世界财富账 | 若将来用于支付，会破坏守恒；当前应视为资产指数 |
| 战争目标未真正执行 | `targetRegionIds` 建立后未参与 `targetPath`；`exhaustion` 初始化后不增长 | 战争仍接近军团自动吃地，目标和战役缺乏连续性 |
| 占领过快 | 野战胜利同季直接 `captureRegion` | 城市、防御、补给和援军缺少故事时间 |
| 每季完整校验历史 | `App.advanceOne` 调用 `validateWorld`；其内部遍历全部 history 并重算 digest | 长局验证成本随历史增长 |
| 自动存档过密 | `App.tsx` 对每次 world 变化启动 380ms debounce 并完整序列化 | 4× 附近可能几乎每季写入数 MB；8× 停止时会集中保存 |
| 地图 LOD 未完成 | 已有 1×～3.6× 镜头，但主要标签逻辑仍按 viewport 紧凑度，而非 zoom tier | 放大后信息密度变化有限 |

### 3.3 本轮实测基线

本轮没有修改模拟代码，只做了只读浏览器与现有审计：

- 现有 `v03-audit`：4 个种子 × 80 季，模拟 Tick P50 `45.917ms`、P95 `56.99ms`、最大 `262.03ms`，最大存档 `4.348MiB`。
- 独立浏览器样本在第 80 季：2238 条历史、234 名人物、441 条关系、存档 `4.79MB`；序列化约 `39.6ms`。
- 同一样本的完整 `validateWorld` P50 `35.9ms`、P95 `51.9ms`。它发生在模拟 Tick 之后，因此真实 UI 季度推进还要叠加校验、React 更新和绘图。
- 另一 160 季样本：3096 条历史、268 名人物、642 条关系、存档 `6.15MB`；完整校验约 `67.8ms`，序列化约 `52.6ms`。

结论：当前仍可玩，但“完整校验 + 全量存档”已经是可证实的长局增长路径。现在先优化它们，比立即引入 Web Worker 更合适。

## 4. vNext 总体架构

### 4.1 新的历史因果循环

```text
环境 / 经济 / 疾病 / 制度压力
             ↓
      Simulation Facts
             ↓
人物记忆 → Desire → Goal → Plan
             ↓               ↓
          Intent          家族策略
             ↓               ↓
      领域 Resolver 执行真实行动
             ↓
      新的 Simulation Facts
             ↓
      Situation 持续更新
             ↓
 Chronicle / 当世三问 / 自动暂停
             ↓
    结果进入记忆与下一轮目标
```

### 4.2 四层数据职责

| 层 | 是否权威 | 职责 | 谁可以消费 |
|---|---|---|---|
| World State | 是 | 当前人口、资源、人物、官职、军队、关系等可变状态 | 各领域 Resolver、哈希、存档 |
| Simulation Fact | 是，追加式 | “实际发生了什么”的不可变事实 | 成长、记忆、Situation、审计、Chronicle 投影 |
| Situation State | 是 | 多季历史进程的当前压力、参与者、阶段与结果 | 人物感知、当世三问、自动暂停、史册聚合 |
| Chronicle Projection | 可重建 | 玩家语言、重要度、史册范围和叙事摘要 | UI、搜索、传记、世界史 |

观察设置、地图镜头、历史筛选和玩家预测仍是非权威状态，不能改变世界哈希。

### 4.3 避免同季循环因果

同一季度内不允许人物因为自己刚刚执行的结果再次无限改目标。采用双缓冲：

1. 季初人物只读取上季已封存 Fact 和本季先发生的非意志环境事实。
2. 人物产生 Intent，但不直接改世界。
3. 各领域 Resolver 执行 Intent 并写 Fact。
4. 季末 Fact 更新 Situation、成长与记忆队列。
5. 新记忆在下一季 Goal Review 时正式影响决策；只有死亡、失去职位等硬失效可以当季终止计划。

## 5. vNext Turn Tick

| 阶段 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 0. 边界输入 | 上季世界、天意干预 | 边界 Fact、季度上下文 | 天意必须带旧 hash 与显式标记 |
| 1. 环境与生产 | 气候、季节、地区、实践 | 产量、灾害、资源 Fact | 先结算自然，再做主体决策 |
| 2. 人口与流动 | 粮食、贸易、迁徙、疾病 | 人口/Shipment/健康 Fact | 守恒账仍由现有系统负责 |
| 3. 生命周期 | 年龄、健康、谱系 | 出生、成年、死亡、继承候选 Fact | 冬季批处理可保留 |
| 4. 记忆与成长 | 上季 Fact、任职、经历 | 记忆聚合、能力暴露量、目标失效 | 不依赖 Chronicle 是否公开 |
| 5. Agency Review | 欲望、目标、关系、Situation、权限 | 目标变更与 Intent | 只有 core/active 人物运行对应深度 |
| 6. 家族与政治 | 家族策略、派系、政治 Intent | 任命、联盟、清洗、妥协等 Fact | 家族默认年度决策，政治按需触发 |
| 7. 外交与战争 | 国家目标、战争、Campaign、军令 Intent | 条约、移动、战斗、围城 Fact | 每场真实交战无条件产出 Fact |
| 8. Situation 更新 | 本季 Facts、驱动信号、旧 Situation | 阶段、张力、里程碑、结果 | 形成与结束都必须有证据 |
| 9. Chronicle 投影 | Facts、Situation、重要度规则 | 世界/国家/家族/人物史条目 | 只筛选展示，不反向决定事实 |
| 10. 季度封存 | 各账本、Fact digest、Situation | lastTurn、hash、增量 invariant | 生产环境不再完整扫描历史 |

## 6. Simulation Fact 与 Chronicle

### 6.1 Fact 的边界

Fact 记录其他系统必须感知的真实发生，不记录每一次内部算术。首批类型：

- Battle：参战军团、主副将、胜负、战损、战场表现、撤退/解散。
- Appointment：任命、免职、调任、军令转移。
- OfficeAction：拒令、削权、清洗、结盟、政变。
- Life：出生、成年、婚姻、死亡、继承。
- Territory：控制权、围城开始/结束、政权建立/灭亡。
- Diplomacy：宣战、条约、背约、和谈、朝贡。
- Economy/Health：只有跨越阈值或改变主体决策的危机事实；普通流量继续保留在 TurnReport。
- SituationMilestone：形成、升级、降温、解决。

Fact 必须最少包含：稳定 ID、季度、类型、参与者及角色、对象引用、结果、结构化差量、来源 Fact、因果证据和审计重要度。

### 6.2 Chronicle 的职责

Chronicle 不再被其他模拟系统读取。它只负责回答：

1. 这件事如何用玩家语言表达？
2. 值得进入哪一本史？
3. 应该展示多少证据？

一个 Fact 可以进入多个范围：

- World Chronicle
- Polity Chronicle
- Region Chronicle
- Family Chronicle
- Personal Biography
- Audit Log

公开重要度改用内部 0～100，UI 继续兼容当前 1～5 星级映射。建议评分由影响规模、持续性、角色地位、Situation 贡献、稀有度与状态差量组成，不允许纯文本规则决定重要度。

### 6.3 兼容迁移

- schema 3 的 `history` 原样保留，不倒推或伪造旧 Fact。
- schema 4 新增 `recentFacts`、`factDigest`、`situations` 等字段。
- `HistoryEvent` 过渡期增加 `sourceFactIds` 与 `situationIds`；旧事件两者为空。
- 第一阶段采用双写：领域系统写 Fact，现有 `pushEvent` 由 Chronicle Projector 生成兼容事件。
- 历史回拨逐步改读 Territory Fact；迁移完成前保留当前 `stateDeltas` 回拨路径。

## 7. Historical Situation 系统

### 7.1 Situation 定义

Situation 是一个持续多个季度、具有张力、参与者、阶段和可解释结果的历史进程。它不是事件文件夹，也不是随机任务。

首版 Situation 状态包含：

| 字段组 | 内容 |
|---|---|
| 身份 | id、type、标题模板、scopeKey、开始/结束季度 |
| 生命周期 | status、phase、tension 0～100、momentum -100～100、phaseSinceTurn |
| 参与者 | 核心人物、支持者、反对者、家族、派系、政权、地区、军队 |
| 驱动 | 结构信号、触发信号、抑制信号及其证据引用 |
| 历史 | 关键 milestone Fact，最近变化，起点快照 |
| 未来 | 可能结果、当前满足度、下一观察信号 |
| 展示 | importance、visibility、当世三问资格、玩家关注状态引用 |
| 结案 | outcome、结果 Fact、影响摘要、结案快照 |

所有可增长数组必须有界：核心参与者建议不超过 12，最近变化不超过 8，开放结果不超过 5；旧证据聚合为 milestone 或摘要。

### 7.2 生命周期

首版只使用三个开放阶段和一个终态，避免状态过多：

```text
emerging  萌芽：信号连续存在，但尚未成为公开危机
active    发展：主体开始行动，玩家可稳定追踪
critical  临界：下一两个行动可能改变制度、领土或人物命运
resolved  结案：生成历史总结，不再参与决策
```

实现上使用 `status = open | resolved` 与 `phase = emerging | active | critical`。降温或正在收束由 momentum 的负值表达，不再增加 `escalating/resolving` 两个易抖动阶段；结案回响属于 UI 展示状态，不属于权威 Situation phase。

形成采用“连续信号 + 滞回阈值”，不采用 `random < p`：

- 候选压力连续 2 季达到形成门槛，才创建 emerging。
- 降到门槛以下 2～3 季才降温，避免一季一变。
- critical 必须同时满足高张力与至少一个可执行主体。
- resolved 必须引用明确结果 Fact，或证明矛盾已连续消散。

随机性只允许影响人物行动是否成功、战场误差或同分选择，不能决定 Situation 是否凭空存在。

### 7.3 更新算法

每类 Situation 由数据驱动模板定义：

1. `candidateKey`：例如“人物 + 所属政权”的军权危机。
2. `signals`：从世界状态与 Fact 生成标准化贡献。
3. `participants`：按职权、关系和实际资源进入，不按姓名脚本。
4. `phaseRules`：带滞回的升级、降温和结案条件。
5. `outcomes`：妥协、清洗、调任、独立、政变等事实条件。
6. `watchSignals`：下一季玩家应观察的变化。

张力描述“离不可逆转后果还有多近”，momentum 描述“正在升温还是降温”。两者不能合并，否则高张力但已缓和的危机会显示错误。

### 7.4 首批模板

按开发顺序而非世界重要度排序：

1. 军权集中 / 将领拥兵自重。
2. 继承危机。
3. 权臣化 / 朝廷派系对峙。
4. 战争与 Campaign。
5. 地方粮食危机。
6. 疫情传播与海上争霸。

疾病不应默认抢占固定槽位；Scenario 和多样性惩罚共同控制其叙事曝光。

## 8. “当世三问”2.0

### 8.1 选择对象

三问主要选择 Situation，而不是每季重新选择裸人物、国家和危机。推荐保持三种阅读尺度：

- 一人：某个核心人物正在改变什么。
- 一国/一家：制度或家族正在如何失衡。
- 天下矛盾：战争、饥荒、海权、疫情等跨实体局势。

它们是展示槽位，不要求 Situation 类型必须刚好属于三类。

### 8.2 连续性规则

- 最短保留 3 季；刚进入的问题不因一季评分波动被替换。
- Situation 结案、失去可见性或被高出至少 20 分且连续 2 季的临界局势压过时才替换。
- 玩家关注的 Situation 不自动退出；结案后保留一季“结果卡”。
- 三槽应用类型、地域和主体多样性惩罚，避免三条都被疾病或同一政权占满。

### 8.3 每张卡必须回答

1. 这件事从何时开始？
2. 目前处于什么阶段，张力如何变化？
3. 上一季具体发生了什么？
4. 为什么会这样？
5. 下一步值得观察什么？
6. 哪些人物和家族在推动或阻止它？

自动暂停应绑定 milestone、phase change、核心人物死亡和结案，而不是 Situation 每季普通数值变化。

## 9. 人物 AI 2.0

### 9.1 设计边界

不做通用心理模拟、不让每个人运行昂贵规划器、不使用 LLM 驱动 NPC。使用少量根欲望、有限目标和人工设计的计划模板。

### 9.2 Desire

把附件中的大量近义欲望压缩为八个根轴：

| 根欲望 | 可以生成的目标示例 |
|---|---|
| 权力 | 获得官职、掌握军令、控制朝廷、独立 |
| 功名 | 立军功、治理名州、完成改革 |
| 家族 | 扶持成员、联姻、保全门第、扩张支系 |
| 财富 | 获取产业、控制商路、保护家产 |
| 安全 | 避战、退让、保护家人、清除威胁 |
| 忠义 | 保护主君、履行承诺、维护正统 |
| 学问 | 学习、传播实践、主持工程或医学 |
| 复仇 | 追究羞辱、背约、杀亲或夺产者 |

改革、独立、获得官职、保护主君属于 Goal，不再各自成为心理轴。

每人最多两个核心欲望、四个动态压力。核心欲望在成年后缓慢变化；重大记忆可以改变排序，但不能每季洗牌。

### 9.3 Goal

核心人物保持：一个长期方向、一个当前主目标、最多两个次目标。Goal 至少记录目标类型、对象引用、起因 Fact、进度、承诺程度、创建时间、复核时间和失效原因。

除死亡、职位消失、对象灭亡等硬失效外，主目标至少保持 4 季。改变目标本身也要产生可追踪的 Agency Fact。

### 9.4 Plan

Plan 不是结果，而是最多五步的行动模板。每一步调用一个领域动作原语，例如：

- 赢得战功
- 寻求提携
- 培养军中支持
- 争取家族背书
- 请求独立统军
- 保留军令
- 拒绝召还
- 寻求妥协
- 发动夺权

人物 AI 只提交 Intent。政治、军事、婚姻和外交 Resolver 检查真实职位、财富、军队、关系、承诺与风险后决定是否执行，并生成 Fact。人物不能直接把自己改成主帅或君主。

### 9.5 从旧公式渐进迁移

现有 `coupScore`、`refusalScore`、`rebellionScore` 不应全部删除。它们先作为“可行性、风险和执行成功率”，不再独自承担动机。

迁移使用 shadow mode：

1. 新 Goal/Plan 正常计算和存档，但旧行为仍决定世界。
2. 审计“新计划建议”和“旧系统实际行动”差异。
3. 先接副将争取统军。
4. 再接抗命、清洗和叛乱。
5. 最后接婚姻、外交和家族战略。

### 9.6 记忆

保留有向 RelationshipMemory，新增有界 PersonalMemory：

- scope：个人、政治、军事、家族。
- salience：重要度与当前目标相关性。
- valence：正负影响。
- subject refs：人物、机构、地区或 Fact。
- pinned：永久关键记忆。

个人记忆建议总上限 16，其中永久记忆最多 4。普通记忆按类型和对象聚合成“多年受到三次削权”之类的摘要。无需再建立一套独立 PoliticalMemory 数组，避免同一事实重复存三份。

### 9.7 经历成长

能力成长来自 Fact 提供的领域暴露量，不显示 RPG 经验条。冬季统一结算：

- 战斗与长期副将任职 → leadership / cunning。
- 治理、赈灾和财政改善 → governance。
- 政治斗争、外交与承诺 → cunning / influence。
- 学习和实践传播 → scholarship 派生能力。
- 航海与水师经历 → maritime aptitude。

成长受天赋上限、年龄曲线、健康和当前能力与上限差影响。普通年份单项最多 +1，重大转折最多 +2；失败也可产生较低学习收益。55 岁后优先用健康与年龄修正有效能力，不必粗暴永久扣除知识。

### 9.8 Simulation LOD

| 层级 | 对象 | 计算频率 | 内容 |
|---|---|---|---|
| Core | 君主、继承候选、高官、主帅、显要家主、Situation 核心人物 | 每季 | 完整 Desire/Goal/Plan/Memory |
| Active | 副将、地方官、继承人、派系骨干、潜在人才 | 收到 Fact 或冬季 | 保留目标与计划，只降低复核频率 |
| Background | 现有背景人物池 | 每年聚合 | 潜力、机会和少量职业信号，不建关系图与计划 |

玩家关注只能改变 UI，不得提升权威 simulation tier。具名人物失势后可以从 Core 降到 Active，但不退回 stub，也不丢传记。

## 10. 家族系统 2.0

### 10.1 两种家族深度

现有 170 左右 Family Entity 不能全部运行家族 AI。引入：

- `great / established`：可行动家族，有战略、资源网络和年度决策。
- `minor / legacy_household`：保留谱系、婚姻和继承，不运行完整家族 AI。

旧存档绝不能按同姓强行合并；这会伪造血缘并破坏婚姻、事件和 familyId 引用。迁移只给旧单人家族标记 `legacy_household`，默认在 UI 折叠。

### 10.2 新世界生成

新世界改成先生成家族模板，再填人物角色：

- 10～15 个大族，每族 4～8 名具名成员。
- 20～30 个中型家族，每族 2～5 名活跃人物。
- 其余人物属于小户、寒门或未形成政治家族的谱系。
- 总可行动家族目标 48～60，不强求精确固定值。

家族需要地域席位、传统、初始关系、官职分布和明确竞争对象，而不只是一组同姓人物。

### 10.3 家族战略

家族每年最多复核一次主战略：保全门第、扩张官职、控制军权、积累资产、联姻结盟、培养继承人。

家主性格只占约三分之一，家族真实结构压力占主要部分。家族不能强制改写成员目标，只能提供或撤回婚姻、财富、提携、官职游说和关系支持，由此产生“个人利益对家族利益”的故事。

### 10.4 字段语义修正

- `polityId` 拆为起源/席位与当前成员分布；家族可跨国任官。
- 若 `wealth` 参与支付，必须进入财富守恒账；若只作评分，应更名为资产指数。
- 家族史以 Situation 与 milestone 聚合，不把每次年度指标变化写成事件。

## 11. 战争叙事演进

### 11.1 分层结论

首版采用：

```text
War
  └─ Campaign（每场战争每方通常 1 个，必要时最多 2 个）
       ├─ Battle Fact
       └─ Siege State / Fact
```

暂不建立独立 Theater Entity。82 节点地图上，Theater 会增加维护成本，却暂时没有足够前线规模证明其必要性。

### 11.2 Campaign

Campaign 记录战争目标、主帅、参与军团、补给路径、目标地区、当前阶段、主动权、损耗和结束条件。阶段为：集结、推进、接敌、围城、巩固、撤退/结束。

`WarState.targetRegionIds` 必须真正约束寻路与和谈；`exhaustion` 必须由战损、补给、持续时间和财政压力增长，而不是只初始化。

### 11.3 轻量围城

有城防的地区在野战失败后不立即转移控制权。围城只保留：守军/民兵、城防、城内粮食、士气、围城进度、疾病压力、援军威胁和当前决策。

每季可能出现投降、突围、援军解围、强攻、内应或继续封锁。控制权只在围城解决后转移；低城防、无守军地区仍可快速占领，避免所有战争被拖慢。

### 11.4 副将与军阀链

陆军与水师使用同一职业 Fact 管线。副将晋升应发生于新军建立、职位空缺、原帅免职或正式扩军，而不是简单与原帅互换职位。

新增 Power Base 概念：直属军令、长期驻地、军中支持者、家族支持、派系和声望共同构成权力基础。这样主帅即使不是地方长官，也可能成为军阀或新势力领袖。

## 12. Historical Narrative Layer

所有重要故事按三层显示：

1. 玩家语言：一句话说明局势与人物选择。
2. 历史证据：事实、关系、军队、资源和里程碑。
3. Simulation Audit：权重、阈值、公式和 RNG 键，仅高级展开。

默认界面绝不能把 debugger 数值当作主要游戏文本。

Situation 结案后自动生成：

- 一段 2～4 句的历史摘要。
- 起止时间、持续季度和阶段曲线。
- 3～6 个关键里程碑。
- 核心人物与家族的得失。
- 领土、合法性、权威、人口或财富的起止差异。
- 后续衍生 Situation。

## 13. 经济、疾病、地图与互动

### 13.1 经济语义化

底层账本不改，UI 增加派生语义：粮食可支撑季数、紧张州数、出生/疾病/战争/饥荒死亡拆分、财政可维持军费季数和下一季风险。

### 13.2 疾病曝光

疾病仍真实模拟，但进入三问的权重受 Scenario、玩家关注、跨区域扩散和叙事多样性影响。普通地方流行不应每盘都压过继承、战争和家族故事。

### 13.3 地图 LOD

- 1×：国号、首都、大军、战争和重大 Situation。
- 1.5×：地区名、港口、普通军团、舰队与 Situation 参与地。
- 2× 以上：商路、疫情、迁徙、地方人物和细化地区指标。

LOD 只改变绘制和命中层，不改变模拟坐标或哈希。

### 13.4 史家预测

预测系统适合观察者体验，但排在 P2。玩家可以预测叛乱、战争胜负或继承结果，预测本身完全不进入 Simulation；结案时只验证判断并形成个人观测记录。

## 14. Scenario 与 Seed

Scenario 决定宏观初始结构和系统权重，Seed 决定具体人物、家族、属性和不确定结果。

首批候选：

- 群雄并起：当前默认模式，政治与战争权重高。
- 大一统末世：一个衰败帝国、弱继承、军门和财政压力。
- 海贸时代：港口、商业、海权和输入性疾病更活跃。

Scenario 不能脚本指定谁称帝或何时叛乱，只能提供可解释的初始条件。该系统应在 Situation 与 AI 稳定后实现，否则只是换一组开局数值。

## 15. 性能与长局策略

### 15.1 P0

1. 把完整 `validateWorld` 限制在创建、读取、导入、手动保存、开发审计和测试。
2. 生产季度只检查本季差量、引用和增量 digest。
3. Autosave 改成 dirty scheduler：至少 4～8 季或 5 秒一次；暂停、重大结案、离开页面时补存；优先 idle 时序列化。
4. 给 Tick 各阶段、校验、序列化和渲染加性能埋点。

### 15.2 P1

- 为季度内反复查询建立局部 Map/Index，不在内层反复 `find`。
- 评估 Character/Relationship/Situation 局部 clone；先测量再引入结构共享。
- Fact、记忆、Situation 最近变化全部有界。

### 15.3 P2

- 将旧 Chronicle 的详细 causes/deltas 转为按年冷档案，热世界只保留近期全量记录和旧史摘要。
- 历史 digest 与 archive digest 继续参与哈希和导出。
- 只有优化后目标移动端仍出现 P95 超预算或连续 Long Task，才引入 Web Worker。

详细数据与预算见 [SIMULATION_PERFORMANCE_AUDIT.md](./SIMULATION_PERFORMANCE_AUDIT.md)。

## 16. 渐进迁移与版本策略

### 16.1 schema 4，而不是原地偷改 schema 3

Fact、Situation 和 Agency 都会成为权威状态，因此应正式升级 schema。产品版本与存档 schema 仍分开：产品可以是 1.x，世界格式升级为 schema 4。

### 16.2 六步迁移

1. Fact 双写：新增 Fact，但不改变旧行为和 UI。
2. Chronicle 分离：成长与记忆改读 Fact，现有史册由 Projector 生成。
3. Situation 监听：只消费当前系统 Facts，先给玩家持续故事。
4. Agency shadow：人物 Goal/Plan 运行但不控制世界。
5. Intent 接管：逐类替换副将、抗命、清洗、叛乱等旧阈值入口。
6. 新世界重构：新的家族生成、Campaign 和 Scenario 只作用于新世界；旧档保留结构。

每一步都必须保持：创建世界、推进、保存、读取、历史搜索、领土回拨和确定性测试可用。

## 17. 风险与控制

| 风险 | 表现 | 控制 |
|---|---|---|
| Situation 变成事件文件夹 | 只有标题和事件列表，没有压力与主体行动 | 每类必须有信号、阶段、结果和下一观察 |
| AI 状态爆炸 | 每人多个计划、记忆无限增长 | 根欲望 8 类、目标 1+2、计划最多 5 步、严格 LOD 与上限 |
| 新旧行为双重执行 | 同一人物被两个系统任命或叛乱 | shadow mode 只记录建议；Intent 接管必须按行为类型设单一 owner |
| 叙事反向污染事实 | 为了好看而虚构战斗或关系 | Chronicle 只能引用 Fact，不得创建权威结果 |
| 旧存档血缘被改写 | 合并同姓家族导致引用错误 | 旧族只分类，不合并；新生成器仅用于新世界 |
| 长局仍膨胀 | Facts、Situation、causes 全量堆积 | 热/冷分层、摘要、digest、有界列表和存档预算 |
| 三问仍频繁换题 | 分数轻微波动替换故事 | 最短保留期、滞回、关注优先和结案卡 |
| 战争拖得过慢 | 所有小城都围城数年 | 只对有防御/守军节点建 Siege，设置投降与快速突破条件 |
| Worker 过早增加复杂度 | 消息协议、复制和调试成本上升 | 先完成校验、存档、索引和 clone profiling，再按数据决定 |

## 18. 总体验收

### 18.1 正确性

- 每次真实战斗都有 Battle Fact；副将经历覆盖率 100%。
- 所有重大意志行为都能追溯 goalId、planId 和 sourceFactIds。
- Chronicle 删除或过滤不影响成长、记忆、Situation 和世界哈希。
- schema 3 存档可读，原有 familyId、history 和领土差量不被重写。

### 18.2 连续性

- 叛乱、政变、夺军权前至少存在准备 Goal 或明确突发硬触发。
- Situation 不因单季普通波动频繁创建/销毁。
- 当世三问能连续追踪同一局势至少 3 季，除非其已结案。

### 18.3 涌现质量

- 100 年样本中能出现副将晋升、家族跨代、继承危机、军阀、权臣和海权故事，但任何单一类型不长期垄断三问。
- 背景人物进入核心历史的比例非零且不过量。
- 不出现永恒和平、永久战争或无法瓦解的单一超级帝国占绝大多数样本。
- 人工 50 年试玩中，测试者能复述至少 5 段有起因、人物、转折和结果的故事。

### 18.4 性能

- 目标桌面季度推进（模拟 + runtime validation）P95 小于 75ms。
- 目标中档移动设备 P95 小于 130ms，8× 不形成持续任务积压。
- 自动存档不因 4× 每季写盘；存档任务不连续阻塞输入。
- 100～300 年档案不超过既定浏览器导入上限，历史搜索仍可渐进加载。

## 19. 明确非目标

- 不扩地图。
- 不增加复杂宗教、文化和文明式科技树。
- 不增加大量资源或兵种。
- 不做 RTS、战棋或即时海战。
- 不让所有 NPC 运行完整认知模型。
- 不用 LLM 替代确定性 AI。
- 不在没有性能数据前引入后端或 Web Worker。

## 20. 最终结论

下一阶段的核心不是“让世界发生更多事”，而是建立三座桥：

1. Fact 把真实发生与公开史册分开。
2. Goal/Plan 把人物属性与长期行动连接起来。
3. Situation 把几十条事实组织成玩家愿意跟随的一段历史。

这三层完成后，现有经济、家族、战争、疾病、海贸和外交才会从丰富数据变成可记住的时代。

具体执行顺序、任务编号和验收门见 [ROADMAP_VNEXT.md](./ROADMAP_VNEXT.md)。
