## 2.2 发布基础设施：版本与游戏内更新闭环

- [x] **INF01 — 可辨识发布与游戏内更新闭环**：参考 `football-for-me` 已验证的部署标识方案，但不为了检查更新提前引入 PWA/Service Worker。每次会触发 Vercel 生产部署的 `main` 更新必须提升 `vX.Y.Z`；构建同时记录 Vercel commit SHA，使玩家既能看懂版本，也能识别同版本误部署或边缘缓存尚未收敛。

### 版本与部署契约

1. `package.json` 是语义版本唯一人工来源；Vite 构建把它注入运行时，并生成不进入预缓存的 `/version.json`，内容至少包含 `version` 与 `buildId`。Vercel 对 `version.json` 使用 `no-cache, no-store, must-revalidate`，`index.html` 必须重新验证。
2. 版本采用 SemVer：修复、文案、UI 和基础设施打磨提升 patch；新的完整玩法纵切提升 minor；只有存档兼容或产品规则发生明确大边界变化才提升 major。任何推送到生产 `main` 的更新都不得沿用上一个部署的版本号。
3. 最新游戏内更新记录与 `package.json` 版本必须一致；发布检查比较上一个生产提交，若生产代码、玩家文案或构建行为变化但版本未提升，则构建失败。commit SHA 仍作为误漏版本或同版本边缘部署的兜底辨识，不取代版本升级。
4. `/version.json` 不进入世界状态、史册、存档或 hash；版本升级默认不等于存档 schema 升级，两者必须继续独立。

### 检查与刷新流程

1. 应用在启动、重新聚焦、回到前台、恢复联网及每 15 分钟静默请求一次 `version.json`；手动“检查更新”复用同一状态机，不另造请求逻辑。
2. 状态只保留“检查中、已是最新、发现新版本、离线、检查失败”五种玩家可理解结果。发现 `version` 或 `buildId` 不同即提示更新，并展示本地版本、远端版本和最近检查时间。
3. 不在季度结算、导入导出、阻塞弹层或自动保存写入中刷新。玩家确认“更新并重载”后先暂停推演并要求 AutosaveCoordinator 完成一次安全 flush，再重新载入；失败时保留当前页面和世界，不进入刷新循环。
4. 普通背景检查不得弹窗、抢焦点或自动中断试玩；只有玩家主动检查或确有新版本时显示明确反馈。

### 游戏内位置与视觉原则

- 不新增顶栏按钮、导航项目或地图悬浮工具。入口放在现有“观察台”滚动区底部，作为一条无卡片的“版本与更新”刊记：左侧显示 `vX.Y.Z` 和短状态，右侧是至少 44px 的“检查更新”文字按钮。
- 视觉论点是“卷末刊记”：常态使用与观察台脚注一致的低对比墨色和细分隔线；发现新版本时才使用既有朱砂强调，并让观察台的原入口出现一个克制小点，不增加第二个入口。
- 内容只包括当前版本、检查状态、操作按钮与最新版 1～3 条简短更新；完整历史默认折叠。文案使用“已是最新”“发现 vX.Y.Z”“更新并重载”，不使用“部署探针、构建指纹、远端资源”等工程术语。
- 交互只保留三种必要反馈：检查按钮短暂旋转、状态文字淡入切换、发现更新时朱砂提示出现；遵守 reduced-motion，移动端不改变观察台宽度和滚动位置。
- 开篇世界书页与其他已有 `V1` 硬编码统一读取同一版本展示值，但不把每处版本文字都做成按钮。

### INF01 验收门

- 本地构建和 Vercel 构建均生成正确的 `version.json`；远端响应确认不缓存，语义版本与部署 commit 可分别识别。
- 发布门禁能拒绝“生产更新但版本未提升”和“最新更新记录与包版本不一致”，并允许纯测试/审计调整按明确规则处理。
- 桌面与 390×844 移动端均能在观察台内手动检查；当前、更新、离线、失败五条路径有测试，按钮和更新确认操作不少于 44px。
- 模拟进行中发现更新不会立即刷新；安全更新前完成暂停与自动存档 flush，刷新后恢复同一世界且不形成重复重载。
- 打开观察台、检查版本或收到远端结果前后，世界 hash、RNG、Fact、Chronicle 和 observer gameplay settings 完全不变。

完成证据（v1.0.1，v1.1.1 补线上路由门禁）：构建生成 `version.json` 并通过发布记录一致性检查；浏览器覆盖当前版本、同版本不同构建、新版本、离线/失败纯函数路径、更新前暂停与 IndexedDB flush，以及桌面/390×844 观察台入口。v1.1.1 进一步要求 Vercel 的 SPA 回退不能匹配 `/version.json`，防止线上端点被首页 HTML 替代。功能归属基线见 [FEATURE_LOOP_INVENTORY.md](./FEATURE_LOOP_INVENTORY.md)。

### Risks

- 每个地区都围城导致战争停滞。
- Campaign 与旧 processMilitary 双重移动。
- 新层级破坏海运和人口/粮食守恒。

### Controls

- 无城防、无守军和低战略节点允许快速占领。
- Campaign 分阶段接管旧军事流程，每次只迁移一个阶段。
- 所有损失继续写现有 TurnReport 账本并跑 invariant。

### Acceptance Criteria

- 高城防重要城市的大多数控制权变化前至少有一季 Siege。
- 每次领土转移都能追溯到投降、占领、登陆或政治交接 Fact。
- 围城人口、粮食、财富与军队损失全部守恒。
- 战争目标实质改变路线、战果与和约。
- 所有 Campaign/Siege 在战争结束后关闭，无悬空引用。
- 强军优势来自兵力、训练、补给和主帅；弱军逆袭必须能展示地形、时机、情报或补给证据。

### 体验层推荐发布顺序

1. 先交付 FUX01，解决移动端“点不准、选中后不知道去哪看、放大后信息不变化”。
2. 再交付 FUX02，让推进季度与人物行动都有清晰的收到、等待和结算反馈。
3. 之后以 FUX03 建立音频底座和最小声景，不在底座完成前大量采购或生成音乐素材。
4. 最后用 FUX04 做全局材质、季节气氛和用语一致性收口；它不得掩盖尚未解决的交互问题。

### Acceptance Criteria

- 新玩家 3 分钟内能关注一条 Situation 并说明其当前矛盾。
- 推进一季后能找到“上一季变化”和“下一观察”。
- 默认界面不直接展示 Utility、Threshold 等审计数值。
- 地图三层 LOD 在桌面与移动端均有视觉/命中自动化测试。
- 查看、筛选、关注、预测和地图操作不改变世界 hash。
- 发布矩阵的控制台错误为 0，键盘、触控和焦点路径可用。
